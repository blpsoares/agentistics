# Claude Code integration — `agentop hooks`

`agentop hooks install` teaches Claude Code to run work in parallel through agentop: when a task
splits into independent pieces, Claude proposes the split, writes each session's prompt, and starts
them all with [`agentop session batch`](session-manager.md#orchestrating-several-at-once) — after
you say yes.

```bash
agentop hooks install      # skill + hook
agentop hooks status       # what is installed, where, at which version
agentop hooks uninstall    # takes back exactly what install wrote
```

Nothing is written to `~/.claude` until you run that command.

---

## First, what a hook actually is

A Claude Code hook is a **deterministic shell callback on an event** (`SessionStart`,
`UserPromptSubmit`, `PreToolUse`, …). It runs a command; if that command prints an
`additionalContext` payload, the text is injected into the model's context.

**A hook infers nothing.** It cannot look at a task and decide it should be parallelised — it is a
shell command, and it runs on every occurrence of its event or on none. The inference is the
**model's**, made afterwards, reading what was injected.

That distinction decides the whole design, because "activate when the task calls for it" is not a
hook's job description — it is a **skill's**. So the integration is two pieces with two different
jobs:

| | **skill** | **hook** |
|---|---|---|
| Where | `~/.claude/skills/agentop-parallel-sessions/SKILL.md` | a `SessionStart` entry in `~/.claude/settings.json` |
| Carries | **knowledge** — when to fan out, how to write each prompt, the exact `session batch` contract | **facts** — which sessions are running *right now*, which is blocked on a permission prompt, which task can be reopened here |
| Loaded | by the model, when the task matches its `description` | by Claude Code, on every session start |
| Costs when unused | **nothing** | **nothing** — the hook prints no output when no sessions exist |

### Why the teaching half is a skill, not a `SessionStart` hook

A `SessionStart` hook that injected the lesson would inject it into **every** session, including the
overwhelming majority that will never start a second assistant — a fixed token tax on every
conversation, paid to be ready for an occasional one. A skill's `description` is matched against the
task at hand and its body is loaded only then. That is literally the mechanism designed for
"activate this by inference", and it is free the rest of the time.

`UserPromptSubmit` was the other candidate: it can read the prompt and inject conditionally. But the
condition it would have to test is *keyword matching against a phrasing* ("in parallel", "at the
same time", "each package") — a heuristic that misses the intent when it is phrased differently and
fires when it is not meant, on every single prompt. The model is better at that judgement than a
regex is, and the skill mechanism already hands it to the model.

### Why the facts half is a hook, not part of the skill

The fleet changes between sessions and cannot live in a static file. A file cannot say *there are
two assistants running in this repository right now and one of them is blocked on a permission
prompt*. That is the one thing a hook is uniquely good at, so it is the only thing the hook does —
and when there is nothing to report, `agentop hooks context` **prints nothing at all** and the
session pays nothing for having the hook installed.

### Why not MCP tools

This repo ships an MCP server ([`packages/mcp`](mcp.md)), and exposing `session_batch` there would
let Claude *call* the thing rather than shell out to it. It is deliberately not done:

- **The executor already exists.** `agentop session batch` is a CLI. Claude runs it with Bash — the
  same way it runs every other command — and the ids come back as JSON with `--json`.
- **Bash's permission prompt is the consent gate.** Starting five assistants is a real, billable
  act. Routing it through Bash means the user sees the exact command and approves it. An MCP tool
  with its own allow-list would move that decision somewhere the user is not looking — the
  integration would gain nothing and lose its only hard stop.

If a read-only `session_list` MCP tool proves useful later, that one has no such objection.

## What gets installed

### The skill

`~/.claude/skills/agentop-parallel-sessions/SKILL.md`, generated by
`packages/server/server/claude-skill.ts`. It names **the harnesses this machine can actually start**
(derived from `SPAWN_SPECS` and narrowed to the CLIs on `PATH`, so it never teaches a command that
would fail), and it teaches:

- when a fan-out is warranted, and when it is not;
- **the consent rule**: propose the split, show the prompts, say how many assistants that is, wait.
  N sessions is roughly N times the cost, and nobody authorised that by asking a question;
- how to write a prompt for a session that cannot see this conversation and cannot ask a question;
- the `session batch` / `list --json` / `open` contract, including that a failed session does not
  abort the rest.

The file carries an **ownership marker** directly under its frontmatter. `install` rewrites and
`uninstall` deletes the file only while that marker is present — delete the line and the file is
yours, permanently.

### The hooks

```json
{
  "hooks": {
    "SessionStart": [
      {
        "hooks": [
          { "type": "command", "command": "agentop hooks context --hook-version 2", "timeout": 10 }
        ]
      }
    ],
    "Stop": [
      {
        "hooks": [
          { "type": "command", "command": "agentop events emit --hook-version 2", "timeout": 5 }
        ]
      }
    ]
  }
}
```

Two events, because they answer two different questions and cost different things.

`SessionStart` has no `matcher`, so it runs on every source (`startup`, `resume`, `clear`,
`compact`) — all of them are moments where this state was just lost or never had.

`Stop` fires when this session finishes answering, and its body writes ONE line into agentop's
[event inbox](session-events.md). It prints nothing into anybody's context and its timeout is five
seconds rather than ten, because it runs at the end of every turn and a budget that is felt is a
budget that is wrong. It is the EXACT half of the event channel: Claude saying it stopped, instead
of the fleet monitor inferring it from the screen up to five seconds later. The channel's poll
source covers the other five harnesses, which have no hook to offer, and is the only thing that can
see a permission prompt at all — Claude Code does not fire `Stop` for one.

Both are planned against the same document and written **once**, so a refusal on the second leaves
neither installed rather than half of the integration in place.

`agentop hooks context` prints either nothing, or one block:

```
<agentop-sessions>
agentop is hosting 2 assistant sessions on this machine. 1 of them is waiting on a person.
  aaaa1111  ·  needs approval  ·  claude  ·  task "auth-refactor"  ·  ~/app
  bbbb3333  ·  working         ·  codex   ·  task "auth-refactor"  ·  ~/app/packages/api
Filed in this directory and not running: "docs-sweep" (2 sessions) — reopen with `agentop session open "<task>"`.
These are facts about this machine, not a request. Do not attach, kill or start sessions unless asked.
</agentop-sessions>
```

Rules it follows (`packages/server/server/session-context.ts`, pure and tested):

- **Only sessions agentop hosts.** An assistant someone started by hand is `external` to the session
  manager: no task, no capturable activity, no id to attach to. Naming it would spend context on a
  row that answers nothing.
- **Reopenable tasks are scoped to this directory** (or below it). Machine-wide they are noise.
- **The block says it is state, not an instruction**, because injected context otherwise reads like
  one.
- **It never fails a session start.** Every error path is silence and exit 0, and the whole read is
  raced against a 4-second deadline (`AGENTISTICS_HOOK_TIMEOUT_MS`). Measured on a real fleet: ~100 ms.

## The install is explicit, and reversible

| Rule | How |
|---|---|
| **The user installs it, not the installer.** | `agentop setup` prints one line suggesting the command (and only while it is not already installed). Nothing writes to `~/.claude` on its own. Same rule `autostart.ts` follows for `~/.bashrc`. |
| **Your `settings.json` is never overwritten.** | Every key, every foreign hook and every key agentop has never heard of is preserved. The merge (`planHookInstall`) adds one entry and touches nothing else. |
| **A file it cannot merge into is refused, not fixed.** | A `settings.json` that is not JSON, whose `hooks` is not an object, or whose `SessionStart` or `Stop` is not an array: agentop reports it and writes **nothing**. |
| **Installing twice changes nothing.** | The second run reports `unchanged` and does not rewrite the file. |
| **Uninstall is the exact inverse.** | Our hook entries go, and the containers that existed only to hold them (`SessionStart`, `Stop`, `hooks`, the skill directory, an empty `skills/`). A group that also carries someone else's hook keeps that hook and its group. Verified byte-for-byte in the tests. |
| **No Claude Code, no files.** | No `~/.claude` and no `claude` on `PATH` → the command says so, exits 1, and creates neither directory nor file. |
| **It never starts a session by itself.** | The skill's first rule is the consent rule; the hook's block says outright not to act on it. |

### Recognising its own entry

Claude Code's hook entry is `{ type, command, timeout }` — there is no field for "who installed
this", and inventing an unknown key in someone else's schema is how a settings file stops validating
on the next release. So agentop identifies its entry by **the command it runs** — one of its own verb
pairs (`hooks context`, `events emit`), plus either `agentop` in the command or the `--hook-version`
flag it always writes — and the version travels in that same command. The match is NARROWED by
event: a `Stop` entry someone moved under `SessionStart` is not ours to delete, or the two hooks
would become one thing that cannot be administered separately. `agentop hooks status` can therefore read a
file it has no memory of writing — one hand-edited, or copied from another machine — with no second
store on the side to disagree with it.

An entry written by a different version is reported as `STALE`; `install` rewrites it **in place**,
keeping the `timeout` and anything else you added to that line.

## Commands

```bash
agentop hooks install   [--hook-only | --skill-only]
agentop hooks uninstall [--hook-only | --skill-only]
agentop hooks status
agentop hooks context            # what the installed hook runs; prints nothing when idle
```

Passing `--hook-only` and `--skill-only` together is refused rather than resolved — together they
mean neither.

```
$ agentop hooks status
claude   ~/.claude
hook     installed v1
         ~/.claude/settings.json
         agentop hooks context --hook-version 1
skill    installed v1
         ~/.claude/skills/agentop-parallel-sessions/SKILL.md
```

| `packages/server/server/claude-hooks.ts` | **pure** | What goes in `settings.json`, how it merges, how our entry is recognised, install/remove/status plans, the `hooks` argv |
